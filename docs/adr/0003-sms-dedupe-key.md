# ADR 0003: Identify an SMS by a day-granular fingerprint

Status: accepted

## Context
The same bank message reaches the database by several routes: the live receiver (via the notification), "Scan old SMS", and a later re-scan or file import. Previously every route inserted a new row (autogenerated id with `REPLACE`), so rescanning a month doubled it.

The receiver sees `SmsMessage.timestampMillis` and the inbox provider has `date`; they are normally equal but not guaranteed to match to the millisecond, so a key that includes the exact time can fail to match the same message.

## Decision
`SmsFingerprint = SHA-256("sms|" + (timestamp / 86_400_000) + "|" + whitespace-normalised body)` stored in a nullable, **unique** `dedupeKey` column. Inserts use `OnConflictStrategy.IGNORE`; a `-1` row id means duplicate.

Rows without an SMS (manual or imported) have a null key, and unique indexes allow many NULLs. Imports are deduplicated by content instead: same second, amount, merchant and direction.

## Alternatives considered
- Exact timestamp + body: breaks when the two sources differ by a few milliseconds.
- Body only: collapses a genuinely repeated identical message across days.
- Sender in the key: the receiver and the provider format the address the same way today, but the extra field adds a failure mode for little gain.

## Consequences
- Two byte-identical messages on the same UTC day are treated as one transaction. Real bank messages include a balance or reference, so this is rare, and it is documented in the README.
- The key is derived data: adding fields later means computing it for old rows with a migration.
